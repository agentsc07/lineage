# Panel Q&A: the final answers and where to see the evidence

| Question | Answer | Evidence |
|---|---|---|
| I uploaded a file. How do you know which repo it came from? | The uploader names a claimed origin; Lineage compares every file hash with what that repo published at a pinned revision, through the hub's API. No claim means trust `unknown`. Hints inside the upload are shown and never trusted. | `lineage/intake/inspectors.py::origin_check`; `tests/test_origin.py`; demo steps 3 and 4 (also against huggingface.co with `LINEAGE_DEMO_REAL_HUB=1`, `tests/test_real_hub.py`) |
| Is any metadata user-editable? | Every fact has a provenance class (computed, fetched, signed, declared). Declared facts are logged with who said them and never raise trust or clear a check: a declared publisher never satisfies the allow list, a declared release date never clears a cooldown. | `lineage/schemas/fact.py`; `tests/test_facts.py`; the Intake page's fact table |
| Can someone edit a passport? | The signature covers every byte. Re-signing needs a key on the trusted-publisher list, and that key's scope must cover the source. | `tests/test_signature_scope.py` (scope mismatch, revoked key, invalid signature) |
| Where does the public key come from? | From the signed policy's trusted-publisher list, which needs 2 of 3 roles to change (`GET /trusted-publishers`). Customers get a vendor's key from `/.well-known/lineage-keys.json`, pinned on first use. The client pins the registry's own key (`lineage pull --pin`). | `lineage_server/routes/trusted_publishers.py`; `lineage/signing/wellknown.py`; `tests/test_wellknown_keys.py` |
| What does `lineage.load()` trust? | Only a registry-signed attestation for this environment, re-checked against revocation and expiry, plus a re-hash of every file. In prod it fails closed when the registry is unreachable. | `lineage/client.py`; `tests/test_load_enforcement.py`; demo step 2 |
| How does a package get controlled? | pip installs only through Lineage's index, which serves admitted wheels pinned by hash, checking the attestation on every request. A blocked release is absent; the newest admitted one resolves. | `lineage_server/routes/simple.py`; `tests/test_package_index.py` (real `pip download`); demo step 5 |
| Is your graph complete? Monitor and revoke depend on it. | Every reference becomes a node; unknown ones are ghosts (status `unregistered`). SBOMs, dependencies, data inputs, bases and federated clients are edges. The monitor runs on a schedule over all of them, ghosts included. | `lineage_server/graph.py`; `tests/test_graph_monitor.py`; demo step 9 |
| What happens when a check cannot run? | It is recorded as `CHECK.NOT_RUN.<name>` and the policy prices it per environment. Never a silent pass. | `tests/test_no_silent_skip.py`; `examples/policy.org.yaml` (`unrun_checks`) |
| How do you detect dataset poisoning? | Format-aware checks (characters, injected content, trigger-to-behaviour, dirty-label triggers, spectral signature, kNN labels, duplicates, PII) and an upstream diff. Measured at 1, 5 and 10% poison; the weak spots are in the results. | `lineage/inspect/dataset_v2.py`; `bench/results_data.md`; demo step 6 |
| Federated learning? | Update scores, robust aggregation, client trust over rounds, a secure-aggregation demo with its limit stated, and a benchmark over 5 attacks. | `lineage/federated/`; `bench/results_fl.md`; demo step 7 |
| A backdoor in a model with no known base? | Template, tokenizer and code checks run; the parent is identified from the weights against a named or admitted base. A weight-only backdoor with no base is an open problem: such a model cannot reach prod without a human, and the unrun weight check has an explicit price. | `lineage/diff/hub_parent.py`; `README.md` limits |
| Who approved this, and could they approve their own request? | The authenticated approver is in the log; the requester of an intake is refused. | `lineage_server/routes/decisions.py`; `tests/test_roles.py`; demo step 2 |
| What does the LLM add over rules? | It judges whether a capability fits the artifact's stated purpose. In precise mode only claims backed by a rule in the same file, or a purpose mismatch, add risk; everything it cites must be a real line. | `lineage/inspect/llm_review/client.py`; `tests/test_inspect_llm_review.py`; `bench/results_after_refactor.md` (reviewer rows) |
| Why not just Trivy or JFrog? | They cover known CVEs, package code and pickle formats. Lineage reuses OSV and the proxy pattern and adds lineage across data, model, fine-tune and package; fine-tune against base; templates and tokenizers; dataset poisoning; MCP pinning and response scanning; federated updates. | `docs/PRIOR_ART.md` |
| What can't you do? | Weight-only backdoors with no base; stolen trusted keys (caught only by inspection and scope); non-text datasets; runtime prompt filtering (Shield); per-client federated scores under secure aggregation. | `README.md` limits |
