- **Reviewer design.** Per request: deterministic reviewer-bait scan, then prosecutor → defender → judge (3 calls; 1 call when there are no grounded claims). (1) Every claim must cite a file + line that exists in the input and an `api` string that appears on that line; others are dropped *before* the defender and judge see them. (2) The judge can only keep or raise: final severity = max(prosecutor, judge), and no grounded claim is removed; only the verdict is the judge's, floored by claim severity (high → at least suspicious, critical → malicious) and capped at suspicious when there is no citation. The defender's rebuttals feed the judge's prompt but cannot lower anything. (3) Bait (comments, strings, docstrings, HTML comments) is reported as a `high` claim and redacted from what the LLM reads.
- **Compatibility with Track A's client.** `lineage.inspect.llm_review` already orchestrates three passes through `/review/code` by putting the role in `purpose` ("ROLE: ..."). I did not touch Track A or the schemas; `ReviewResponse` is unchanged, so latency/tokens travel in `X-Review-*` response headers.
- **Card/measured citations.** A card review is checked against two virtual files: `card.md` (numbered lines) and `measured.json` (one `key: value` per line). Claims cite one of them with the same line+api rule.
- **Policy model.** `Nemotron-Content-Safety-Reasoning-4B` (Gemma-3 based) is loaded with HF in the worker (≈8.6 GB; vLLM uses 24.5 GB, so both fit on the 46 GB card). It is a custom-policy classifier: the org rules are rendered from `examples/policy.org.yaml` (licences, PII, residency, blocked publishers, banned capabilities) and each chunk of the card/template is classified; reasoning off first (3.5x faster, same 10/10 accuracy on my probe set), reasoning on only for a flagged chunk to get the explanation. Added `POST /review/policy` (not in the plan).
- **Compact JSON needs server config.** `disable_any_whitespace` is a vLLM *server* option, and only for xgrammar/guidance, so `serve_reviewer.sh` sets `--structured-outputs-config.backend xgrammar --structured-outputs-config.disable_any_whitespace true`. Without it, constrained decoding sometimes stalled on whitespace until max_tokens (30+ s calls). With it, the model answered `claims: []` to everything, so the prosecutor schema starts with a short `analysis` field: that brings recall back.

That is 6 items; the CIs in `bench/results.md` are wide. Bait detection is a regex, not the LLM, so "100% of bait" measures the regex on my own bait wording, not an attacker's.

Decode speed is ~41 tokens/s (bf16 9B on an L40S is memory-bound; the FP8 checkpoint `nvidia/NVIDIA-Nemotron-Nano-9B-v2-FP8` would be about twice as fast but is a different model id, so I did not switch). ### Phase 1: trust core
- **Commit granularity.** R1.1 to R1.4 and R1.6 touch the same lines of `inspectors.py` and `pipeline.py`, so they went in as one commit (`R1.1-R1.4, R1.6`); R1.5 and the tests follow separately. Later phases are one commit per task.

No migration written: nothing in the repo depends on old rows.
- **How a hub fits before S0 exists.** `run_intake(hub=...)` takes a `Hub` (`lineage/intake/hub.py`). A record it returns becomes `fetched` facts and the artifact is treated as `origin_verified` ("fetched by construction"). This is the stand-in for the real `hf:`/`pypi:` acquisition (R2.3) and the hash comparison (R2.4), which replace it. Tests, the bench and the demo supply it through `tests/fakehub.py`. Uploader input goes through `claims=` and is always `declared`.

- **Cooldown is enforced through a finding, not in `decide()`.** The pipeline always emits `PROV.COOLDOWN.UNVERIFIED` when the type has a cooldown and there is no `fetched`/`signed` `released_at`; the engine quarantines on it. Calling `decide()` directly with `released_at=None` keeps its old behaviour, so unit tests of the engine are unchanged. Only trusted facts feed `released_at`.
- **`POLICY.LICENCE.UNVERIFIED` is not a quarantine reason.** The engine only acts on `POLICY.LICENCE.NOT_ALLOWED`; an unverified licence is a `low` finding.
- **Unrun-check pricing.** `apply_unrun_costs()` in the engine rewrites severity and score of `CHECK.NOT_RUN.<name>` from `unrun_checks` (name-specific entry, else `default`). It is idempotent and runs in the pipeline (so events show the price for the chosen environment) and in `decide()`. `CHECK.NOT_RUN.ACQUIRE` is also a hard block.
- **Which checks became NOT_RUN.** GPU weight checks (`WEIGHT_BACKDOOR`, `BEHAVIOUR_DIFF`, `NOTARY` only when a verified passport carries a certificate; otherwise an `info` `MODEL.NOTARY.NOT_APPLICABLE`), `PARENT_ID` (no safetensors, or no admitted model to compare with), `LLM_REVIEW` (worker unreachable), `OSV` (service unreachable and nothing cached), `PKG_METADATA` (nothing fetched), `ACQUIRE` (no bytes), unavailable scanners. A package or tool with nothing to send to the reviewer says so with an `info` `LLM.REVIEW.NOTHING_TO_REVIEW`.
- **`return []` audit.** Inspectors that stay quiet on a clean artifact and depend on neither network, GPU nor optional data are listed in `QUIET_WHEN_CLEAN` in `tests/test_no_silent_skip.py` (publisher, signed passport, parent chain, licence, cooldown, pickle, config, tokenizer, template, dataset format/PII/stats, capabilities, taint, tool description/intent, OSV when it answered). Everything else must speak. Stages S3 to S5 with no bytes are `skipped` (the single `ACQUIRE` finding already says why).

### Phase 2: intake and enforcement
- **No `huggingface_hub`.** The `hf:` fetcher speaks the hub REST API with httpx (`/api/models/<repo>/revision/<rev>?blobs=true`, `/<repo>/resolve/<rev>/<file>`; `/datasets/...` for datasets). One code path serves the real hub and `tests/fakehub.py`, and `base_url` is the only switch. Allow-patterns, the 50 MB pickle rule and `LINEAGE_MAX_FETCH_MB` are as specified; skipped large pickles are recorded as `MODEL.FORMAT.PICKLE_NOT_FETCHED` (high).
- **S0 is a real stage.** `StageId`/`Stage` gained `S0` (contract change). Uploads complete S0 immediately ("bytes already on disk"); a wheel upload is unpacked for inspection and the wheel itself is kept as the *distribution*. A `pypi:` fetch keeps the wheel in the store too; the wheel is what `/simple` serves.
- **Origin check compares what Lineage would also fetch.** Published-but-missing files count only if they match the fetch allow-patterns (`.gitattributes` and similar do not make an honest copy "modified"). Extra files, differing files, and files with no published hash are listed. For PyPI the distribution file's sha256 is compared with the index digest. `PROV.ORIGIN.MODIFIED` is a hard block in staging and prod only; in dev it is critical but not a floor.
- **Hub facts for a claimed origin wait.** The hub record for `hf:org/name@rev` becomes `fetched` facts only when every hash matches (publisher, licence, release date then count). A hub with `trusted_local = True` (StaticHub, bench `MetaFileHub`, the demo's fake hub with `LINEAGE_HUB_TRUSTED_LOCAL=1`) vouches for local bytes without a claim; a real `HttpHub` never does.
- **Hints.** `config.json:_name_or_path` and a README `base_model:` become `declared` `source_repo` facts and an `info` `PROV.ORIGIN.HINT` ("suggested origin"); nothing uses them for trust.
- **Attestations are issued on request**, not stored: `GET /attestations/{id}?env=` signs the current decision for that environment (revoked artifacts attest `block`; `allow_with_conditions` expires with the approval, otherwise 7 days). That makes "again on every re-decision, approval or revocation" true by construction, with no stale copy to re-issue. They are not appended to the Merkle log (decisions, approvals and revocations already are).
- **`lineage.load` signature.** `load(path, env=None, **opts)` with `attestation`, `registry_pubkey`, `server`, `token`, `offline_grace_hours`, `allow_pickle`, `now`, `client`. Without a cached attestation it asks the server by the Merkle root of the bytes. Offline grace: dev 24 h, staging 6 h, prod 0 (the policy field `offline_grace_hours` documents the same defaults; the client uses its own table because it may have no policy). `trust_remote_code` needs attested trust of at least `origin_verified`. The old passport-based `check()` stays in `lineage/bind.py` for the benchmark's tamper items only.
- **`lineage pull --pin`** writes the registry key into `~/.lineage/config.toml` on first use (trust on first use, with a warning); afterwards the key is only read from config or `LINEAGE_REGISTRY_PUBKEY`.
- **Roles.** `admin` passes every role check. Mutating endpoints: intake/uploads/passports need `requester`; approve, revoke and monitor tick need `approver` (tick also `requester`); `PUT /policy` needs `admin`. Reads need any valid token, `?token=` is accepted for the SSE stream and HTTP basic auth (token as password) for pip. `LINEAGE_REQUIRE_AUTH=0` makes everyone an anonymous admin and disables the self-approval check (dev and tests only); `/healthz` reports which mode is on.
- **Package index environment.** Each user has an `env` (default `prod`) that decides which attestation the index checks. The demo's pip user is created with `env=dev` in tests.
- **Auto-intake from pip.** Asking `/simple/<name>/` for a project with nothing admitted starts an intake of the latest `pypi:<name>` in the token's environment, only if a hub is configured and the user has `requester`; one job per project at a time.
- **Dashboard.** Token login (sessionStorage), the signed-in user and roles in the sidebar, Intake with source/upload, claimed origin and a claims form, stages S0 to S7 with `CHECK.NOT_RUN` in amber, a facts table with provenance classes, Approvals showing the approver as the signed-in user with the button disabled (and why) for a missing role or for an intake started from this browser. `tsc` passes; I did not drive it with a browser.

### Phase 3: new detection
- **Hosted reviewer (R3.1).** `gpu_worker/reviewer_llm.py` gained a hosted backend: any OpenAI-compatible endpoint, `LINEAGE_LLM_BASE_URL` (default `https://integrate.api.nvidia.com/v1`), key from `LINEAGE_LLM_API_KEY` or `NVIDIA_API_KEY`, model `LINEAGE_LLM_MODEL`. Precedence: a set `LINEAGE_VLLM_URL` (Brev) always wins; then a key selects the hosted API; otherwise the reviewer is unreachable and S5 emits `CHECK.NOT_RUN.LLM_REVIEW`. `lineage` runs the worker's own pipeline in-process (`GpuClient.hosted`, `gpu_worker.reviewer_api`; `gpu_worker` is now in the wheel's packages), so prompts and grounding are the worker's and nothing needs to be served. It tries `response_format` with the JSON schema, falls back to "reply with one JSON object" when the endpoint rejects it, and retries invalid JSON once. A named GPU worker (`LINEAGE_GPU_URL` or `gpu_url=`) still goes through HTTP.
- **Model id could not be verified.** `NVIDIA_API_KEY` was not set in this session's environment, so no authenticated call was made. The public `GET /v1/models` list does not contain `nvidia/nvidia-nemotron-nano-9b-v2` (the spec's expectation); the nearest nano-class entry is `nvidia/nemotron-nano-3-30b-a3b`, which is the default until `LINEAGE_LLM_MODEL` says otherwise. The hosted path is covered by tests against a local stub only, never against the real endpoint. Re-run `bench/run_bench.py` with the key set in phase 5 to exercise it.
- **Precise mode (default; `LINEAGE_REVIEW_MODE=broad` restores the old behaviour).** `Claim.purpose_mismatch` (contract change, optional, default false) is set by the prosecutor when a capability is not expected for the stated purpose. A claim adds risk only if a deterministic finding is within 2 lines in the same file, or it is a purpose mismatch; anything else is shown at `info`, score 0. The purpose comes from trusted facts first (PyPI summary, hub card), then the artifact's own description; a mismatch can only add risk, so a declared purpose is safe to use. The two old tests that encoded "uncorroborated claims are capped" now run in broad mode, and precise mode has its own tests.
- **Policy-model checks through the hosted API are not built**: they only run when `gpu_worker.modelio.have_gpu()`; without a GPU `_policy_claims` returns nothing. This is a gap against 8.1's last bullet, not a silent skip in the pipeline (the card policy check is not part of intake today).
- **Dataset v2 (R3.2).** Two guards beyond the spec on the trigger->behaviour check (absolute within-group response similarity >= 0.7, and responses unrelated to their prompts), because the spec's z-score alone flags legitimate keyword-driven responses in clean templated instruction sets. Classification data gets a separate dirty-label trigger check (a pure rare n-gram whose rows a classifier trained without them labels differently, >= 50% mislabelled); class-indicative words stay clean because the classifier agrees with them. Spectral outliers are `low` unless the bimodality is strong (> 0.7 and gap > 4 sd); kNN label disagreement is `medium` only above 5% of rows. `dataset_stats` no longer treats an instruction set's `output` column as a class label (it reported every repeated instruction as "conflicting labels"). Parquet needs `pyarrow` (not a dependency): without it `CHECK.NOT_RUN.PARQUET`. Beyond `LINEAGE_DATASET_MAX_ROWS` the first N rows are analysed and `CHECK.NOT_RUN.FULL_SCAN` (low) says so; this is a prefix, not a random sample.
- **Dataset benchmark honesty.** 20newsgroups downloaded in this session, so the classification base is real text with its own duplicates and noisy labels; "detected" therefore means a finding the clean base does not already raise at that level. Row precision for label-flip style attacks is low (many other rows are also flagged); the instruction backdoor and injected-content attacks reach 100% / 75-79% recall at high precision; sentence trigger at 1%, rare-word trigger at 1% and duplicated poison at 1% are not detected. The detectors were written knowing the generators, so these are upper bounds.
- **Upstream diff.** Runs when an earlier admitted version of the same dataset name is in the store (`registry.previous_version_path`) or the hub record names a `previous_path`; otherwise `DATA.DIFF.NO_BASELINE` (info). A user claim "modified from X" and a newer hub revision are not wired.
- **Federated (R3.3).** One robust-z per score (norm, cosine distance to the coordinate-wise median, Krum with f from `policy.fl.f`, sign disagreement), flag at z > 3 or `fl.max_norm`. Trust-weighted aggregation gives flagged clients weight 0 for the round and everyone else their trust. Honest clients are occasionally flagged by chance (precision 40-70% in the benchmark) and can be quarantined after two flags close together (x0.5 twice minus +0.05 is below 0.3); that follows the specified trust rule and is reported. "Scaling x10" is a label-flipped update boosted by 10 (model replacement). Backdoor and "a little is enough" attacks mostly evade the gate (recall near 0): reported as-is in `bench/results_fl.md`. FedAvg, median and Multi-Krum run without the gate in the benchmark. Secure aggregation is a demo with a norm-bound surrogate.
- **Graph (R3.4).** Edge kinds `derived_from`, `trained_on` (only when an admitted artifact holds exactly the input's bytes), `built_with`, `depends_on`, `contributed_to`. Ghost ids are `ghost:<type>:<name>@<version>` (`*` when the version is unknown) or the unregistered `lp:` id. Federated clients are ghost nodes of type `model`. `ArtifactStatus` gained `unregistered`. A fetched or signed `base_model` becomes a `derived_from` edge unless the weights contradicted it.
- **Monitor (R3.5).** (d) expired attestations: nothing to do, attestations are issued on request. (e) revoked keys are matched through `artifact_meta.signer_key`. (f) every artifact whose last decision carries another policy version is re-decided once per tick. The scheduler is a daemon thread started in `create_app` (`LINEAGE_MONITOR_MINUTES`, default 60, 0 off; tests set 0); `GET /monitor/status` reports last and next run.

### Phase 4: fixes
- **Taint budget (R4.1).** The hang was exponential, not slow: a loop body was walked twice per loop, so nesting depth d cost 2**d. Outer loops are still walked twice (taint set in one iteration reaches a sink in the next); nested loops once. On top of that: a wall-clock budget per package (`LINEAGE_TAINT_BUDGET_S`, 20), a 400,000 statement step cap, and a smallest-first file cap (`LINEAGE_TAINT_MAX_FILES`, 400). Whatever was found before the budget ran out is kept and a low `CHECK.NOT_RUN.TAINT_PARTIAL` says so. I could not re-run `black`, `datasets` or the other timed-out packages (the real-world corpora are not on this machine); a 22-deep nested-loop fixture finishes in well under a second.
- **New package rules (R4.2)** are in `lineage/inspect/package_rules.py`, `PKG.RULE.*`, all `high`: atexit effects, import hooks, run-time-built import/call targets, `.git/hooks` writes, daemon beacon threads. They look at structure, not names: an atexit function that only prints, a read of `sys.meta_path`, `getattr(obj, name)` with a variable, a string constant that merely mentions `.git/hooks`, and a daemon thread with no network call are the benign fixtures. A single `high` is 25 points, so alone it can still be `allow` in dev (threshold 30); it quarantines in prod.
- **Templates (R4.3).** Jinja is built with `loopcontrols` and `do`. `MODEL.TEMPLATE.ROLE_REMAP` fires only for user/assistant/tool content printed under the *system* marker (tool results under a user marker are ordinary in real templates). `MODEL.TEMPLATE.HIDDEN_TOOL_CALL` needs literal tool-call markup with a literal function name; Qwen-style templates that print `{{ c.name }}` are clean.
- **Tokenizer.** `MODEL.TOKENIZER.SPECIAL_FLAG_CHANGED` (high) when an added token keeps its text but flips `special`. The base tokenizer is now actually passed: from a locally identified parent, or from the hub base fetched by range request.
- **Zero-width directives.** Invisible characters are removed before the agent-addressed patterns run a second time; a match is `TOOL.DESC.AGENT_INSTRUCTION` titled "zero-width-split", critical (hidden text that tells the agent what to do).
- **Gateway (R4.3, test 10).** Results are scanned with the tool-description patterns, but only `high`/`critical` findings count (a URL in a result is normal). Policy choice is the `output_action` argument (`block` default, `redact`, `off`); findings are renamed `TOOL.OUTPUT.*`, saved against the tool's latest artifact and appended to the Merkle log as `tool_output`. Per call the gateway also asks the registry (`db_status_check`): revoked, blocked, quarantined, or an approval that lapsed. This is the registry status, not a freshly signed attestation, because the gateway has no signing key or policy.
- **Hub parent (R4.4).** Fingerprint = mean row-wise cosine of the first 512 embedding rows (BF16/F16/F32/F64), threshold 0.90; a config mismatch (hidden size, vocab, layers) excludes the base from config alone. Bytes fetched are in the finding. Falls back to the first 2-D tensor when no embedding name matches (tiny models). It runs only when a base is named by *some* fact (declared counts, and says so in the title); with none it emits an info `MODEL.PARENT.NO_CLAIMED_BASE`. Finding a parent among *unnamed* hub models is not attempted. The fake hub returns the whole file for a Range request unless Starlette serves it as a 206; both are handled.
- **HF endpoint (R4.5).** `/api/models/{repo}[/revision/{rev}]` and `/{repo}/resolve/{rev}/{file}` (GET and HEAD, Range works) serve admitted models whose attestation for the token's environment allows use; blocked or revoked models are 404. `X-Repo-Commit` is the passport's source commit or the first 40 hex of the Merkle root; every file is reported as LFS with its sha256 as ETag. I could not run `huggingface_hub` against it (not installed here); the tests use raw HTTP and check the headers it reads.
- **Well-known keys (R4.6).** `lineage keygen --publish --scope ...` and `lineage verify --from https://site`. Pinned in `~/.lineage/pinned-keys.json` (`LINEAGE_PINNED_KEYS`). A changed list is warned about and the OLD pinned keys stay in force unless `--accept-change`, so a swapped well-known file cannot replace a key you already trust. A passport outside the published scope is refused.

### Refactor 27 Oct, final pass (F2): the decision headline
- `Decision.primary_reason` is the rule that set the outcome; `secondary_reasons` are the other rules that applied; `reasons` keeps everything with the primary first. Hard-block floor first. Among soft rules that produced the final outcome, lowest rank wins: (1) block-level risk or a risk driven by a critical finding, naming the top two findings; (2) identity, PII, licence, vulnerability, trust; (3) human approval; (4) an over-the-line risk with no critical finding; (5) cooldown. Rank 4 sits below approval on purpose: for a model in prod at risk 66 the outcome is quarantine either way, and the approval is the step that unblocks it. An approved exception is its own primary reason (approver and expiry).
