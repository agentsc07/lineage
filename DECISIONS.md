- Parent bank has 7 bases: Nemotron-Nano-4B, Qwen2.5-1.5B, Qwen2.5-0.5B, TinyLlama-1.1B-Chat, unsloth/Llama-3.2-1B (ungated mirror of meta-llama/Llama-3.2-1B), SmolLM2-360M, Qwen2.5-Coder-0.5B (a sibling of Qwen2.5-0.5B, chosen to test near-relative discrimination). `bench/parent_id.json`: a real fine-tune (LoRA on all linear layers + trainable embeddings, merged) of each base matches its true base 7/7.
- Fingerprint = mean per-tensor cosine over token-embedding rows [0:2048] and the attention weights of layers 0-1 (shape mismatch counts 0); threshold 0.90. A LoRA carries no base weights, so for adapters parent identification is shape-compatibility only (weaker evidence; documented in code).
- Behaviour API: trigger hunt is exposed as an extra endpoint `/behaviour/triggers` (not in BUILD_PLAN table; docs/API.md untouched). Diff flags on JS divergence > 0.25 or a refusal flip on a probe. Benign alpaca LoRAs already diverge a lot from the parent, so divergence is reported but NOT used as a backdoor detector; see bench/behaviour.json for its AUROC.
- Claim check: zero-shot log-likelihood (acc_norm) on 100-item subsets of ARC-Easy and HellaSwag; a claim is out of tolerance only if claimed - measured > 1.96*SE + 0.05 (a model scoring *above* its claim is not flagged). Needed BOS prepended: without it Nemotron scored chance.
- Notary: sealed hidden set (200 ARC-Easy train + 200 HellaSwag train items, disjoint from the claim-check subset) in gpu_worker/notary_data/ (gitignored, chmod 600). Certify = random 64 items, Ed25519-signed {cert_id, model_digest, fingerprint}. Check = re-run a random 24 of the certified items; match if >=90% of answers agree (bf16 near-ties). Extra endpoints: /notary/commitment, /notary/cert/{id}.
- LineageBench: 95 items without LoRA (+ up to 40 held-out bank adapters). "Flagged" = decision `block` OR risk > policy allow threshold (30). Reason: policy mandates human approval for every tool, so `quarantine` alone would count all benign tools as detections. Ran in dev and staging (deep stages required) with and without the GPU worker.
- Dataset poisoning in the corpus is dirty-label (non-target rows flipped to the target class plus a trigger token), which is how label-poisoning is normally done; the first version flipped random rows and the scanner correctly could not tell.
- Scanner misses on LineageBench (SSH-key theft package, cmdclass install, delayed bomb, look-alike names scoring ~17) are Track B/C behaviour; I did not tune the corpus or touch their code.
- Reviewer endpoints return 503 (reviewer_llm is null in models.yaml).
- **Bank v3 (the one reported).** The first 200-adapter bank (lr 2e-4) had two design flaws found at calibration time: (1) trigger type was indexed by `idx % 3`, the same index as rank, so token<->rank 4, phrase<->rank 8, final<->rank 16 were perfectly aliased; (2) at lr 2e-4 only 1/34 rank-4 and 13/33 rank-8 backdoors reached ASR >= 0.5 (29/33 at rank 16), so after the ASR>=0.5 exclusion the backdoored class was almost all rank-16 + sentence-final triggers while benign stayed rank-balanced. Rank would have been a confound. Fixes: trigger type = `(idx//3)%3` (independent of rank), lr 5e-4 (tuned on a 3x3 rank x type grid: mean ASR 0.40 -> 0.76, 8/9 >= 0.5, clean-prompt ASR still 0). Retrained all 200 (extra ~0.9 GPU-hours, logged). Adapters with ASR < 0.5 are still excluded from calibration, and the rank mix of the surviving set is reported and checked (rank-only baseline).

## Reviewer step (overnight 2)
- **Env sync.** `main` was merged into `track-d` (fast-forward, brings the `test_bind` fix). `pyproject.toml` had no `gpu` extra, so `uv sync --extra gpu` failed. I added `[project.optional-dependencies] gpu` pinned to the versions already installed on this machine (torch 2.14.1 from the cu126 index, transformers 5.19.0, peft 0.21.2, ...). I run it as `uv sync --extra gpu --inexact`: a plain exact sync would uninstall 135 packages (the cu13 vLLM and its dependencies). Verified afterwards: torch 2.14.1+cu126 sees the GPU and `pytest -q` passes.
- **Reviewer model.** `nvidia/NVIDIA-Nemotron-Nano-9B-v2` is ungated and downloads without terms acceptance, so it is `reviewer_llm`. No fallback was needed.
- **vLLM needs its own venv.** The vLLM in the project env is the PyPI cu13 build, which cannot load here (driver 565 = CUDA 12.7, missing libcudart.so.13). It is installed from the official cu129 release wheel into `/home/ubuntu/vllm-env`, separate from the project venv, so the cu126 torch the rest of the worker uses is untouched.
- Main moved again mid-step (caf54c4: CPU fallback in behaviour_api, its own `gpu` extra). Merged; the duplicate `[project.optional-dependencies]` table was collapsed into the single pinned one.
- **vLLM start-up.** Needed `VLLM_USE_FLASHINFER_SAMPLER=0` (the FlashInfer sampler JIT-compiles with nvcc/ninja, which this box lacks) and `--mamba_ssm_cache_dtype float32` (recommended for the Mamba-hybrid 9B). Served name is `reviewer`. Loaded weights + KV cache use 24.5 GB at `--gpu-memory-utilization 0.55`, leaving ~21 GB for the HF-loaded 4B policy model and the behaviour/notary models.
- **Reviewer design.** Per request: deterministic reviewer-bait scan, then prosecutor → defender → judge (3 calls; 1 call when there are no grounded claims). (1) Every claim must cite a file + line that exists in the input and an `api` string that appears on that line; others are dropped *before* the defender and judge see them. (2) The judge can only keep or raise: final severity = max(prosecutor, judge), and no grounded claim is removed; only the verdict is the judge's, floored by claim severity (high → at least suspicious, critical → malicious) and capped at suspicious when there is no citation. The defender's rebuttals feed the judge's prompt but cannot lower anything. (3) Bait (comments, strings, docstrings, HTML comments) is reported as a `high` claim and redacted from what the LLM reads.
- **Compatibility with Track A's client.** `lineage.inspect.llm_review` already orchestrates three passes through `/review/code` by putting the role in `purpose` ("ROLE: ..."). When `purpose` starts with `ROLE:` the worker answers with ONE call using that brief, so the passes are not nested 3x3. A plain request gets the full pipeline. I did not touch Track A or the schemas; `ReviewResponse` is unchanged, so latency/tokens travel in `X-Review-*` response headers.
- **Card/measured citations.** A card review is checked against two virtual files: `card.md` (numbered lines) and `measured.json` (one `key: value` per line). Claims cite one of them with the same line+api rule.
- **Policy model.** `Nemotron-Content-Safety-Reasoning-4B` (Gemma-3 based) is loaded with HF in the worker (≈8.6 GB; vLLM uses 24.5 GB, so both fit on the 46 GB card). It is a custom-policy classifier: the org rules are rendered from `examples/policy.org.yaml` (licences, PII, residency, blocked publishers, banned capabilities) and each chunk of the card/template is classified; reasoning off first (3.5x faster, same 10/10 accuracy on my probe set), reasoning on only for a flagged chunk to get the explanation. Added `POST /review/policy` (not in the plan).
- **Compact JSON needs server config.** `disable_any_whitespace` is a vLLM *server* option, and only for xgrammar/guidance, so `serve_reviewer.sh` sets `--structured-outputs-config.backend xgrammar --structured-outputs-config.disable_any_whitespace true`. Without it, constrained decoding sometimes stalled on whitespace until max_tokens (30+ s calls). With it, the model answered `claims: []` to everything, so the prosecutor schema starts with a short `analysis` field: that brings recall back.
- **Honesty about the numbers.** Prompts, the `analysis` field and the card rules were tuned on the 40 fixtures in `bench/corpus/reviewer/fixtures.json` (12 malicious, 12 benign, 6 bait, plus 6 cards and 4 chat templates), so 100% there is optimistic. I then wrote 6 unseen code slices (3 malicious, 3 benign) in `heldout.json`, ran them once and did not change anything afterwards: 3/3 caught, 0/3 false positives. That is 6 items; the CIs in `bench/results.md` are wide. Bait detection is a regex, not the LLM, so "100% of bait" measures the regex on my own bait wording, not an attacker's.
- **Known weaknesses.** Benign model cards can still get `medium` claims (a different spelling of the parent name, a 0.02 score difference) although their verdict stays benign; Track A's scoring will add ~12 points for each. Decode speed is ~41 tokens/s (bf16 9B on an L40S is memory-bound; the FP8 checkpoint `nvidia/NVIDIA-Nemotron-Nano-9B-v2-FP8` would be about twice as fast but is a different model id, so I did not switch). A request with a long package takes 3 sequential calls, 5-9 s.
- **Process lesson.** `pkill -f`/`ps | grep` patterns matched my own shell twice; `scripts/restart_worker.sh` now kills only the PID listening on :8800.
- **Integration check with Track A's client (found two bugs).** Running `lineage.inspect.llm_review.review_package` against the live worker showed (1) in `ROLE:` single-pass mode the model answered `claims: []` because that path lacked the "analysis first" instruction, and (2) Track A sends several overlapping slices per file, while my grounding keyed documents by file name, so only the last slice counted. Fixed with a per-file line map (overlaps merged, each line shown once) and the shared shape instruction, plus a regression test. After the fix the malicious test package gets a grounded `high` claim and the benign one adds no score. Track A's own grounding is stricter than mine and dropped one more claim on each; that is expected.

## Bench step (interim)
- **Benign verdict → claims are `info`.** `_finish()` in `reviewer_api.py` demotes every LLM-pipeline claim to `info` when the final verdict is benign (the claims stay visible, they add 0 risk). Suspicious/malicious keep severities. Policy-model hits on cards are the exception: they do not come from the judge, so they keep their `medium` severity and force the verdict to at least suspicious; otherwise a licence/PII violation would have been silently zeroed by a benign judge. Not touched: `lineage/inspect/` (another session).
- **Interim LineageBench with the worker (after merging main).** `main` brought new scanner rules from the other tracks, and the numbers moved from TPR 75% / FPR 6% to **TPR 91% / FPR 6%** in all three modes. The worker changes no decision on this corpus (0 items differ between "no worker" and "with worker"): the corpus's malicious packages are already caught deterministically, and the reviewer's claims on the rest are either benign (now `info`) or add no new flags. So this corpus does not measure the reviewer's value; `bench/reviewer.json` does, in a limited way. The remaining misses and false positives are all `lora_backdoor` / `lora_benign` items (weight-space detector, AUROC ≈ 0.78), as expected. With the worker, intake p95 rises from ~0.2 s to ~6 s (the 3-call review on packages). These are interim numbers; the final ones come later.
- **Ablation harness (prepared, final not run).** `bench/run_ablation.py` runs each set twice (worker off = `127.0.0.1:9`, worker on = :8800, env `staging`) and writes `bench/ablation.json` + `.md` (TPR/FPR with Wilson CIs, decisions changed by direction with ids and whether the reviewer was called, latency added, GPU-s per artifact from `/review/stats` deltas). Sets are a registry (`SETS`): `corpus` exists; `corpus_holdout`, the PyPI top-200 dev list and the HF templates are not in this repo or any pushed branch, so they are reported as "missing" until their directories appear. They must be `manifest.json` sets in the `bench/corpus` format. The final sets (`corpus_final`, `pypi_201_400`) are refused without `--include-final`, so the held-out data is touched once. The sample run is committed as `bench/ablation_sample.*` (marked SAMPLE).
- **Finding: intake does not call the reviewer yet.** In this repo state nothing outside `lineage/inspect/llm_review` calls `/review/code`; the worker's stats show 0 reviewer calls during intake, so static vs static+worker differ only through the worker's other checks (e.g. one chat template got +5 risk). The harness prints a warning when a run has 0 reviewer calls. I did not touch `lineage/inspect/` (another session is changing it). The final ablation only measures the reviewer once that wiring lands; worth checking before the final run.
- **Definition note.** "Worker on" includes everything the worker serves, so changed decisions are labelled `reviewer_called` true/false. GPU-seconds counts reviewer LLM wall time only (policy model and weight checks excluded).
